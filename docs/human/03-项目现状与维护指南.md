# 项目现状与维护指南
## 先知道现在交付了什么

这是一个本地单页游戏原型，核心源码与运行资源都已在项目内。它没有后端、数据库、账号系统或运行时模型调用。

**截至 2026-10-20 的游戏基线**：35 条故事中 34 条通过，1 条由用户主动 blocked。最后一轮游戏代码修复提交为 `f656c88`，验收与文档记录提交为 `cde83d4`。当前人类文档与分享包装建立在这份基线上。

# 接手时先看这几个入口

| 要做什么 | 从哪里开始 |
| --- | --- |
| 修改玩家看到的界面 | `src/ui/`、`src/style.css`、`index.html` |
| 查找场景接线与渲染 | `src/game/scenes/ArenaScene.ts` |
| 修改角色、敌人、波次数值 | `src/game/data/`，再核对对应纯逻辑模块 |
| 修改战斗、强化或存档规则 | `src/game/` 下对应模块和 `tests/` |
| 重画角色与场地 | `tools/generate-assets.mjs`；输出到 `public/assets/` |
| 制作轻量分享版 | `tools/release/build-share.mjs` 与 `npm run build:share` |
| 修改这套手册 | `docs/human/*.md`、`docs/human/figures/*.svg` |

## 日常开发与交付

```bash
npm run dev -- --port 5343 --strictPort
npm run typecheck
npm run lint
npm run test
npm run build
```

只改文档时，不需要重新跑四角色游戏；修改规则后跑受影响测试，发布前再检查构建和关键界面。角色图片改过时，必须看实际画面，不能只看 PNG 是否存在。

`ArenaScene.ts` 承担较多场景接线。增加能力时优先把纯规则留在独立模块，避免继续把所有逻辑塞进场景类；这是维护建议，不代表本次已经做了结构重构。

# 验收结果：通过与跳过分开看

## 已有的有效证据

- 最后一次完整质量检查：**589 个测试**通过；typecheck、lint、build 通过。
- 压力场景维持 80 敌人、40 弹体、3 流形，浏览器前台采样 60 秒，平均 **58.25 FPS**，满足平均至少 50 FPS 的验收条件。
- 连续重开 5 次后，设置订阅保持 2；DOM 监听总数保持 89，document 监听 12、canvas 监听 8。此前每局增长的问题已修复。
- 这是该机器、该浏览器与该压力场景的测量，不把平均 FPS 写成“所有电脑始终 60 FPS”。

证据文件：`docs/perf-runs/perf-2026-10-20T02-31-47-562Z.json`；对应截图在 `screenshots/perf/`。

## 用户主动跳过的部分

US-026a 的“四角色正常规则完整通关与全键盘流程自动试玩”没有自动通过。用户已自行检查并明确要求跳过，所以保持 **blocked=true、passes=false**。不要把这项改写成“全部 35 条均通过”，也不要重新启动通关机器人填补记录。

## 分享包装的额外核对

单文件版在 macOS / Chrome 155 断网、file:// 环境下完成菜单、角色图片、进入战场与检查点写入检查。原生字母键的自动化复核受工具限制，保留首次运行的人工检查项；这与既有游戏基线的 589 个测试不是同一组证据。

## 当前边界

这是单人桌面原型，不含联机、账号、云存档、永久战力、移动端触控或手柄支持。难度和长局手感不应仅由测试数量推断。分享版主要验证文件分发与离线兼容，不重新承诺已跳过的通关结果。

# 文档、记录与维护分工

## 给人阅读

- `docs/human/01-游戏说明书.md`：玩家操作、角色、强化与续玩。
- `docs/human/02-分享与启动指南.md`：发包、打开、存档限制与重建命令。
- 本文件：实现范围、维护入口、验收事实与已知边界。
- `output/pdf/`：这三份文档的 PDF；SVG 原图随 MD 保留。

## 保留给工程追溯

`tasks/`、`scripts/ralph/prd.json`、`progress.txt`、`docs/patterns-*.md` 与 `docs/project-state-*.md` 仍保留。它们记录开发过程，不是玩家说明书，也不进入轻量分享包。

自动开发循环已经结束。玩游戏用 `npm run dev` 或离线 HTML，不要再启动 Harness。

## 后续修改的安全习惯

1. 先 `git status`，保留现有未提交改动和本机存档。
2. 用功能分支改代码，检查受影响测试与实际画面。
3. 重新构建分享文件；在解压后的副本上验证打开，而不是只验开发服务器。
4. 发布前检查包里没有私密配置、日志或浏览器数据；保留软件许可说明。
5. 如果需要换模型重新自动开发，应单独确认新任务范围，不沿用已经结束的故事清单。
